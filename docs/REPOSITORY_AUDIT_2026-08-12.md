# 경화수월 저장소 종합 감사

작성일: 2026-08-12
기준 커밋: `a06956a`
감사 브랜치: `codex/full-repository-audit`

## 결론

현재 빌드는 플레이 가능한 프로토타입을 넘어, 규칙 엔진과 콘텐츠 검증이 잘 갖춰진 게임입니다. `game/`이 React에 의존하지 않고 `UI → reducer → engine/content` 방향을 지키며, 247개 테스트가 짓·끗패·수집·부적·금단패·상점·저장·모바일 레이아웃의 주요 회귀를 막습니다. 보안 감사와 두 배포 빌드도 모두 통과했습니다.

다만 유지보수 비용은 여전히 높습니다. 이번 구조 작업으로 `GameApp.tsx`는 2,068줄에서 1,604줄, `game/state/game.ts`는 1,916줄에서 1,503줄로 줄었지만, `pixel-direction.css` 2,465줄과 그 안의 `!important` 463개는 다음 병목으로 남아 있습니다.

즉, 전면 재작성은 필요하지 않습니다. 순수 엔진과 테스트는 보존하고, 화면 조립·상점 상태 전이·스타일 계층·배포 자산만 경계별로 나누는 것이 가장 안전합니다.

## 감사 범위와 근거

- `app/`, `game/`, `worker/`, `build/`, `scripts/` 구조와 의존 방향
- 게임 규칙, 콘텐츠 카탈로그, 상점·계약·보스·저장 흐름
- CSS 계층, 모션, 툴팁, 모바일 가로 모드, 접근성 코드

- README, 인수인계, 밸런스, 과거 작업 문서의 현재성
- 테스트·타입·린트·일반 빌드·GitHub Pages 빌드·의존성 보안 감사

이번 감사는 자동 검증과 코드·자산 검토를 기준으로 했습니다. 별도의 신규 플레이테스트나 브라우저별 픽셀 단위 시각 비교는 범위에 넣지 않았습니다.

## 잘된 구조

### 규칙 엔진의 방향이 올바르다

`game/content`는 선언형 데이터, `game/engine`은 순수 계산, `game/state`는 상태 전이를 맡습니다. `game/`에서 `app/`을 가져오는 역참조도 없습니다. 이 분리는 유지해야 하며, UI 정리 때문에 엔진을 React 훅 안으로 옮겨서는 안 됩니다.

### 선택 순서가 게임의 핵심 규칙으로 고정돼 있다

플레이어가 처음 고른 두 장이 끗패, 세 번째 이후가 짓입니다. 같은 월의 강화·효과 여부와 관계없이 월값으로 땡과 끗을 판정하고, 짓은 나머지 카드의 출력 월 합이 10의 배수일 때만 성립합니다. 이 규칙은 자동 최적 분할보다 조작과 결과의 인과가 명확합니다.

### 콘텐츠 데이터와 구현을 테스트가 잇는다

현재 카탈로그 기준은 부적 56, 화공패 15, 금단패 10, 비결서 22, 각인 8, 판본 4, 낙관 4, 시작 덱 5, 우두머리 12, 팩 11, 계약 8쌍입니다. 카드 효과 12종도 단순 문구가 아니라 득점·수집·드로우·버리기·정산 경로에 연결되어 있습니다.

### UI 안전장치가 누적돼 있다

툴팁은 `document.body` 포털과 공통 위치 계산기를 사용하고, 제출 중 버튼 잠금·점수 공개 지연·수집판 착지·부적 성장 연출이 별도 상태로 관리됩니다. 모바일 가로 모드와 `prefers-reduced-motion` 회귀 테스트도 존재합니다.

## 우선순위별 개선 사항

### P0 — 즉시 막아야 할 오류

현재 자동 검증에서 P0는 발견되지 않았습니다.

### P1 — 다음 대형 기능 전에 처리

#### 1. 장터 규칙의 단일 출처 만들기

**상태: 완료.** 실제 진열과 구매가 `engine/economy.ts`의 가중 추첨·원자적 구매 경로를 사용하며, 보정 규칙은 `state/market-actions.ts`에 모았습니다.

감사 당시에는 실제 장터가 엔진의 가중치를 쓰지 않았습니다. 현재는 `market-actions.ts`가 엔진 함수를 호출하므로 데이터 희귀도와 실제 진열 확률이 일치합니다.

권장 조치:

1. 실제 reducer가 `generateSeededOffers`, `purchaseShopOffer`, `rerollShop`을 호출하게 전환합니다.
2. 튜토리얼 첫 부적, 보유 부적 제외, 금단패 연속 중복 방지, 대서고 보장은 입력 보정자로 둡니다.
3. 기존 state 테스트를 동일 결과의 계약 테스트로 유지한 뒤 중복 함수를 삭제합니다.

이 항목은 단순 코드 미관이 아니라 “설명과 실제 확률이 다른” 게임 밸런스 문제입니다.

#### 2. `GameApp`을 조정 훅과 화면 라우터로 분리

**상태: 대부분 완료.** 저장·오디오·제출·금단 연출 훅과 팩·술잔·규칙 모달을 분리했습니다. 최상위 화면 라우터의 추가 분리는 CSS 경계 작업과 함께 진행합니다.

감사 당시 `GameApp.tsx`가 저장 복원, 음악, 제출·버리기·금단 연출, 팩·술잔 모달을 모두 소유했습니다. 현재 이 수명주기와 모달은 독립 파일로 이동했고, 화면 분기와 플레이 화면 조립만 다음 분리 대상으로 남았습니다.

권장 추출 단위:

- `useGamePersistence`: 저장 로드, 지연 저장, flush
- `useGameAudioScene`: 음소거, 장면 전환, 첫 상호작용 활성화
- `useSubmissionPresentation`: snapshot, beat, 수집 착지, 점수 공개 잠금
- `useForbiddenPresentation`: 금단장 대상과 결과 연출
- `GameScreenRouter`: `title / intro / play / reward / shop / contract / end` 분기
- `PackPickModal`, `CupChoiceModal`, `RulesModal`은 별도 파일

화면이 읽는 파생값은 selector 함수로 옮기되, 게임 규칙 계산을 UI selector에서 새로 구현하지 않아야 합니다.

#### 3. reducer를 도메인별 명령으로 나누기

**상태: 1차 완료.** selector, 장터, 팩, 소모품, 로그, 계절 전환을 별도 모듈로 옮겼습니다. 제출·라운드 수명주기는 결합도가 높아 다음 묶음에서 테스트를 보강한 뒤 이동합니다.

감사 당시 `game/state/game.ts`가 33개 액션과 모든 도메인을 포함했습니다. 현재 `gameReducer`라는 단일 공개 진입점은 유지하면서 장터·팩·소모품·selector·계절 전환을 분리했고, 제출·라운드 수명주기가 다음 대상입니다.

- `run-lifecycle.ts`: 시작, 월 시작, 보상, 다음 월, 무한 달력, 패배
- `round-actions.ts`: 선택, 제출, 술잔, 버리기, 고·스톱
- `market-actions.ts`: 진열, 구매, 재선택, 판매, 계약
- `consumable-actions.ts`: 화공패·금단패 대상과 적용
- `selectors.ts`: 요구 점수, 유효 부적 칸, 현재 끗패 미리보기

각 함수는 `GameState → GameState` 형태를 유지하고 reducer는 액션 라우팅만 담당하면 됩니다.

#### 4. CSS 계층을 명시적으로 다시 세우기

현재 큰 CSS는 `pixel-direction.css` 2,465줄, `game-ui.css` 2,048줄, `game.css` 1,524줄입니다. 특히 픽셀 방향 파일에 `!important`가 463개 있어 반응형 수정이 기존 규칙을 다시 덮는 방식으로 누적됩니다.

권장 순서:

1. `@layer reset, tokens, layout, component, art, motion, responsive, overrides`를 선언합니다.
2. 화면별로 `play / market / intro / title / end / modal` 파일을 나눕니다.
3. 카드 비율·툴팁 z-index·모바일 safe area 같은 불변 토큰을 한 곳에 둡니다.
4. 동작을 바꾸지 않는 선택자 이동부터 하고, 시각 회귀 확인 후 `!important`를 구역별로 줄입니다.

한 번에 CSS를 다시 쓰는 방식은 현재 시각 품질을 깨뜨릴 위험이 큽니다.

#### 5. 배포 자산을 실행 자산과 제작 원본으로 분리

**상태: 완료.** 제작 원본을 `source-assets/`로 이동하고, 런타임 manifest와 36MiB 예산을 배포 검증에 연결했습니다.

감사 당시 `public/`은 약 66.7MB였습니다. 현재 실제 실행 자산만 남겨 31,206,337바이트로 줄였으며 카드 화질·재생 음악·효과 구성은 유지했습니다.

권장 조치:

- 게임이 직접 읽지 않는 생성 아틀라스와 편집 원본을 `source-assets/` 또는 릴리스 제외 폴더로 이동합니다.
- WebP 48장을 정상 경로로 유지하고, PNG 48장 fallback은 별도 선택 다운로드나 빌드 검증 자산으로 전환합니다.
- 긴 BGM은 청감상 차이가 없는 범위에서 Opus/OGG 비트레이트와 무음 구간을 정리합니다.
- 빌드 시 `assets/manifest.json` 기반 allowlist로 `public/` 산출물을 생성합니다.
- 동일 바이트인 비결서·부적·소각 팩 크기별 그림 8개는 한 파일을 공유하도록 매핑합니다.

카드 그림 해상도, 이펙트 개수, 음악 구성은 유지하면서 전송량만 줄일 수 있습니다.

#### 6. 배포 전에 전체 검증을 의무화

**상태: 완료.** Pages 배포는 자산 검사·테스트·타입·린트를 먼저 통과해야 하며 Dependabot과 주간 production 보안 감사를 별도로 실행합니다.

감사 당시 Pages workflow는 빌드만 실행했습니다. 현재는 `verify` 작업이 성공해야 정적 export와 배포가 시작됩니다.

`verify` job에서 테스트·타입·린트를 통과한 뒤에만 Pages build/deploy가 실행되도록 바꾸고, 의존성 보안은 Dependabot 또는 별도 주기 작업으로 분리하는 것이 좋습니다.

### P2 — 안정화 이후 개선

#### 접근성

- `GameModal`은 초점 진입은 하지만 Tab 포커스 고정, 닫은 뒤 원래 요소로 복귀, 배경 `inert` 처리가 없습니다.
- 부적 드래그 순서는 포인터에는 자연스럽지만 키보드용 왼쪽·오른쪽 이동 조작이 노출되지 않습니다.
- 의미 있는 ARIA와 `prefers-reduced-motion`은 이미 있으므로, axe 기반 자동 검사와 키보드 시나리오 테스트를 추가하면 효과가 큽니다.

#### 빌드 경고

Vite가 향후 native config loader에서 JSON import attribute와 로컬 import 확장자를 요구한다고 경고합니다. `vite.config.ts`의 JSON import와 `sites-vite-plugin` import를 다음 Vite 대형 업데이트 전에 정리해야 합니다.

#### 호스팅별 보안 차이

Cloudflare Worker 응답에는 CSP, COOP, CORP, Permissions-Policy, nosniff, frame 방지 헤더가 있습니다. 주 배포 링크인 GitHub Pages에서는 같은 응답 헤더를 설정할 수 없습니다. 현재 앱은 서버 데이터나 비밀키를 사용하지 않아 직접 위험은 낮지만, 보안 헤더가 필요한 배포를 기준으로 삼을 경우 Worker/Sites 쪽을 주 배포로 승격해야 합니다.

#### 저장 스키마

브랜드가 `경화수월`로 바뀌어도 `flower-board-go:v2` 키는 기존 저장 호환을 위해 유지해야 합니다. 이름이 어색하다는 이유만으로 변경하지 말고, 실제 스키마 비호환 변경 때만 새 키로 이관하십시오.

## 게임 디자인 피드백

### 강점

- 처음 고른 두 장을 끗패로 삼는 조작이 규칙 설명과 전략을 동시에 만듭니다.
- 제출 점수와 고스톱 수집 점수가 한 판 안에서 경쟁해, 즉시 점수와 장기 수집 사이 선택이 생깁니다.
- 부적 순서, 비결서 성장, 카드 효과, 화공패·금단패, 계절 계약이 서로 다른 시간축의 성장을 담당합니다.
- 3·6·9·12월 우두머리와 계절 결산이 12월 캠페인의 호흡을 나눕니다.

### 개선하면 좋은 점

1. **빌드 정체성 요약**: 덱 화면과 장터에 현재 런의 강점을 `끗패 / 긴 짓 / 광 수집 / 띠 수집 / 경제 / 소각` 같은 2~3개 태그로 요약하면 56개 부적을 외우지 않아도 방향을 잡을 수 있습니다.
2. **희귀도와 등장 확률의 신뢰성**: 장터 단일 출처 작업과 함께 실제 확률 또는 `흔함·드묾` 정도를 설명에 표시하십시오.
3. **우두머리 대응의 지속 표시**: 월 시작에서만 읽게 하지 말고 플레이 레일에 “이번 판 방해 / 대응 한 줄”을 접어서 남겨 두면 기억 시험이 아니라 전략 문제가 됩니다.
4. **무한 달력 변주**: 목표 ×1.6만 반복하기보다 두목 규칙 2개 조합, 날씨 강화, 장터 제약 중 하나를 시드 기반으로 붙이면 후반 반복성이 줄어듭니다.
5. **도감의 발견성**: 족보·부적·금단패를 `미발견 / 발견 / 이번 런 사용`으로 나누고, 실제 발동 예시를 한 줄 기록하면 콘텐츠 양이 학습 보상으로 바뀝니다.
6. **결산의 학습 피드백**: 최고 손패뿐 아니라 가장 많이 기여한 부적, 수집 점수 비율, 구매 후 점수 상승을 보여 주면 다음 런의 선택 근거가 생깁니다.
7. **튜토리얼 층 분리**: 첫 판에는 선택 순서·짓 성립·수집 착지만 가르치고, 고·금단·계약·부적 순서는 상황별 첫 등장 도움말로 미루는 편이 부담이 적습니다.

### 유지할 방향

- 낮은 족보와 높은 족보, 일반 월과 보스 월의 연출 계층을 분리한 구조는 타격감의 기준이 됩니다.

### 보강할 방향

1. **아트 바이블 1장**: 팔레트, 테두리 굵기, 질감 밀도, 광원 방향, 금박 사용량, 입자 크기, 카드·책·부적 2:3 안전 영역을 수치로 고정하십시오.

3. **입자보다 큰 형태**: 보스 계절감은 작은 사각 파티클 수를 늘리기보다 꽃잎·빗줄기·낙엽·서리처럼 계절별 큰 실루엣과 깊이층을 쓰는 편이 고급스럽습니다.
4. **강조 예산**: 상시 반짝임은 카드 재질에만, 큰 화면 섬광은 높은 족보·보스·금단 결과에만 허용해 시선의 희소성을 지키십시오.
5. **생성 이미지 후처리 규칙**: 동일한 대비, 테두리, 종이결, 채도 범위로 정규화하고 원본 프롬프트보다 최종 게임 내 축소 화면을 승인 기준으로 삼으십시오.
